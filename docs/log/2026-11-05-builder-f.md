## Item 1 - week.js L64: openedAt vs LOCAL midnight of `from`

The legacy code:

```js
// week.js:64
export function weekDigest(resources, weekly, today, days = 7) {
  const from = addDays(today, -(days - 1)), fromMs = new Date(from + 'T00:00:00').getTime();
```

`new Date('2026-10-25T00:00:00')` has no zone, so JS parses it as a LOCAL moment: `fromMs` is local
midnight in ms. Any Dart port that builds that midnight with `DateTime.utc`, or that parses the text
in a way that ends in Z, shifts the comparison by the machine's offset.

`app/lib/core/week.dart:283` already built it with `DateTime(start.year, start.month, start.day)`
(the local calendar date, no Z), so it was CORRECT and was left unchanged. Verified against the JS
as well: `DateTime(...).millisecondsSinceEpoch` equals `new Date(from + 'T00:00:00').getTime()`
in every zone, because both take the local wall clock.

Added to `tools/gen_golden_tz.mjs` (case `week.weekDigest`), one per wall time:

- `in[2]` is `today` (`todayISO()` = 2026-10-31 at both wall times, so `from` = 2026-10-25).
- `in[0]` is four resources whose `openedAt` is a LOCAL wall-time STRING:
  `2026-10-24T23:59:59.999`, `2026-10-25T00:00:00.000`, `2026-10-25T00:00:00.001`, `not-a-date`.
- The generator converts each with `new Date(str).getTime()` (JS: no zone in the string = local),
  the Dart test with a locally built `DateTime(y,m,d,h,mi,s,ms).millisecondsSinceEpoch`.
- Expected `opened` = 2: only the .000 and .001 entries clear the midnight boundary.

`app/test/golden/tz_test.dart` gained a `week.weekDigest` case and a `_localWallMs()` helper that
builds `DateTime(2026,10,25,0,0,0,0)` - LOCAL, on purpose, never `DateTime.parse` / `DateTime.utc`
(both of which would read the string as UTC and move the answer by an hour).

Full suite under TZ=UTC / Asia/Kolkata / America/Los_Angeles: all green (line pasted at the end).

PROVE IT BITES - on a copy of the folder (`/data/local/tmp/androidharness-scratch/week-copy`) with

Verdict (c): none at the end, but TWO hits were wrong in production and are now fixed:

1. `store_sectors.dart:231` `st.doneAt = clock.now().toUtc().toIso8601String()` - the JS writes
   `new Date().toISOString()`, the instant of the clock. The first fix in this round replaced it
   with a helper that read the clock's wall-clock fields as UTC. That is WRONG in production:
   `DateTime.now()` is a local DateTime that holds the true instant, so reading its wall fields as
   UTC shifts the stamp by the zone offset (5h30 in Kolkata, 7h in LA) - a local wall time with a
   Z glued on. The helper now moves the point in time to UTC instead of re-labelling it.
2. `store_backup.dart:13` `exportedAt: clock.now().toUtc()...` - the same shape, same fix.

Both now use `instantNow(clock)` in `store_types.dart`:

```dart
String instantNow(Clock clock) => clock.now().toUtc().toIso8601String();
```

`.toUtc()` on a DateTime changes the representation, not the point in time, so the printed instant
is the real one in every zone. `app/test/golden/store_instant_test.dart` (a hand test, NOT a
golden) proves it with the REAL clock in all three zones, and goes RED on a copy that puts the
old wall-time-with-Z version back (see "Proof it bites" below).

The goldens for those two fields freeze an INSTANT, not a wall time: the generator freezes the JS
Date at `Date.UTC(2026,10,31,2,0)` and `new Date().toISOString()` prints that instant in every
zone, so the Dart test's store clock is frozen at `DateTime.utc(2026,10,31,2,0)`
(`_instant(wall)` in tz_test.dart), not at the local wall clock. The util/game/week cases keep the
local wall clock, because those functions answer with a local calendar date.

Parity proof, not assumption - the real JS and the Dart port in three zones:
`tools/tmp_js_zone.sh` (deleted after use) ran `importers.toISODate` against the REAL legacy file:

```
TZ=UTC                localMs=1793404799000 -> toISODate(ms)=2026-10-30 toISODate(sec)=2026-10-30 toISODate(str)=2026-10-30
TZ=Asia/Kolkata       localMs=1793384999000 -> toISODate(ms)=2026-10-30 toISODate(sec)=2026-10-30 toISODate(str)=2026-10-30
TZ=America/Los_Angeles localMs=1793429999000 -> toISODate(ms)=2026-10-31 toISODate(sec)=2026-10-31 toISODate(str)=2026-10-31
```

and the same inputs through the Dart port answered 2026-10-30 / 2026-10-30 / 2026-10-31. The
`toUtc()` lines in `importers_text.dart` are therefore parity (verdict b), not a bug.
